# How I Use Cursor という投稿の和訳

元リンク: https://x.com/poteto/status/2058975157503570132

## Cursor の使い方

心の中に溜め込んでいたことがあった。面接前の `@cursor_ai` には、実際には Cursor を使ったことがなかった。

Meta では Claude Code が急速に広がっていた。  
サイドプロジェクト用に、個人で月額 200 ドルのプランを払ってまで使っていた。  
とてもシンプルで、生産性がすぐに上がる点が好きだった。  
問題だったのは、Claude Code を「ほぼ何にでも使える」ものに変える自分だけのスキルセットを作ることだった。  
そのために、上に乗せるエージェントオーケストレーターのツールを自作し始めた。

対面面接では 2 日間にわたって Cursor を使い、面接課題を作成した。これは Cursor 3 がリリースされる前だったため、Editor Window を使っていた。  
この時点で私は長年 vscode を使っていたので、ほとんどのショートカットはまだ体に馴染んでおり、IDE に戻るのはそれほど難しくなかった。  
とはいえ正直に言うと、最初の 1〜2 時間は CLI がないことが明確に足りなかった。  
クリック操作がほぼ「野蛮に」感じられた。

ただ、いくつか明確に印象に残った点がある。

まず、当時使っていたモデル（Opus と Codex）が、なぜか賢く感じられた。  
しかも、ふつうに必要な瞬間にモデルを切り替え、プロジェクトの異なる部分で同時に両方を使えるのがうれしかった。  
例えばフロントエンドは Opus、システム系は Codex。  
面接の前からすでに「複数モデルによるアドバーサリアルレビュー」を推していたので、UI 上でこの体験が自然にできたのは非常に自然だった。

さらに良かったのは、異なるモデルのサブエージェントを起動できることだ。  
ひとつの会話で両方の長所を取り出せた。

次に、コンパクションが異常に速かった。  
cc ユーザーとしては、これまでコンパクト化に何分もかかるため、常にコンテキスト量やプラン利用状況を気にしていた。  
Cursor ではその速度に愕然とした。  
ほぼコンテキスト使用率を見なくても済むほどだった。  
cc ではコンパクション後にモデルが急に「バカになる」ように感じることが多かったが、そういった感覚はほとんど起きなかった。

三つ目は、TUI より GUI がどれだけ価値を生むかだ。  
Cursor のブラウザでアプリを直接開けて、Design Mode でデザイン変更できるのは直感的だった。  
この体験から、用途を前提化した UI が、エージェント型コーディングをどれだけ有効にできるかを改めて考えた。

## Cursor を Cursor で作る

3 月末から参画して以来、主に Cursor 3 の Agent Window を使い、日常的にこれを起動している。  
cc 自体は素晴らしいチームで作られた良い製品だと考えている一方で、シンプルすぎるため、人々がそれを囲む独自抽象化を作りたくなる傾向があることも見てきた。  
前職では、毎週のように cc の上に新しい社内オーケストレーターが発表されるような感じだった。

`@bcherny` は「レイテンシ（潜在需要）」についてよく話していた。  
> 「製品には『潜在需要』という古い考えがある。  
> 使いやすい形で「改変できる（ハッカブルな）」製品を作ると、思わぬ用途への使われ方が起きる。  
> そうなると、実際の使われ方を見て、さらにそれに合わせたものを作っていくことになる」

まさにそれだ。  
オーケストレーションツールへ人々が集まるのは、実際、CLI だけだと結局人間がオーケストレーターとして立つ構図が露わになるからだ。

ただ、これまで使ってきたエージェントワークフローは、たいてい本質からずれていた。  
GUI 上で複数の CLI を動かすだけではポイントを外している。  
自分が追っているのは、エージェントへの「信頼」をどう設計するかだ。

元エンジニアリングマネージャーとして、エージェント運用は人のエンジニアリングチーム運営に近いとすぐに気づいた。  
新規メンバーは、コードベースの理解だけでなく、仕事の進め方まで理解できるようにオンボーディングが必要だ。  
彼らはすでにデバッグ、品質の高いコード/テスト作成、コミュニケーションなど、過去の経験から得たスキルを持って参加してくる。

エージェントは、常に記憶喪失に近い新規採用者のようで、少し愚直な状態に近い。  
教えたことを忘れ、新しいことはほとんど自発的に学ばない。  
だからこそ、ルール、スキル、ツール、長期記憶を与えて近づけることができる。  
能力はあるが素朴で、学習可能性が高い。  
私は彼らの失敗パターンを、深く厳密なエンジニアリングを伝えるチャンスとして捉えている。

厳密さがないと、エージェントはお世辞を言うようにでも、依頼されたコードを生成し続ける。  
しかも、かなり大量に書いてしまう。  
不用意な並列化は、ただ「早く大量に」雑なコードを増やすだけになりがちだ。

> 4 月 26 日  
>  
> 私はますます、複数エージェントを並列化する価値は「広く浅く」ではなく「狭く深く」にあるという確信に近づいている。  
> 単独か少数の課題を掘り下げる方が、良い結果を出す確率は高い。  
> それが N 分岐競争の良い点だ。

## 速く進めたいなら、まず深く行け

エージェントのオーケストレーションは生産的にできると思っている。  
ただし、深さ優先で進めるべきだ。

私は自分の **pstack** を OSS として公開した。  
これは、日々 `@cursor_ai` を作るために使っている個人的なスキルとエンジニアリング原則だ。  
サイドプロジェクトで初期版を作り始め、以降継続して改良してきた。

入手先: https://cursor.com/marketplace/cursor/pstack  

```
/add-plugin pstack
```

これらのスキルは Cursor チームでかなり使われるようになった。なので、みんなに共有するのが楽しみだ。

Cursor の社内リーダーボードでは、今週 9k 回使われた。  

pstack は複数モデルを使って、エージェントにより厳密な振る舞いを教える。観測した失敗パターンをすべてスキル化した。  
このプラグインの中核は `/poteto-mode`。  
これは、タスクに応じた適切な手順を返す高位スキルだ。  
狙いは「LOC を最大化すること」ではなく、その逆だ。  
最小限のコードで最大のインパクトを出すことが目的だ。

厳密性のあるアプローチは、経験豊富なエンジニアと同じ流れで問題に向き合うことから生まれる。  
例えばデバッグは問題空間の二分探索が良い。  
最初に仮説を立て、系統的に排除して真の根本原因に近づく。  
再現しづらいときは、バグを人工的に再現しやすくすることもある。  
あるいは実行中の状態を確認するために計測やコンソールログを追加する。  

これらは「推測で終わる」ことなく、徹底的にデバッグするための playbook だ。  
pstack にはこの厳密性を実現するスキルと playbook が多数同梱されている。  
現在用意されているものには次がある。

- スキル作成と評価
- 自律実行
- バグ修正とランタイムフォレンジック
- 機能開発
- ビジュアルの一致確認とプロトタイピング
- そのほか多数

厳密性が必要な場面では、プロンプトの先頭に `/poteto-mode` を付ける。例:

```text
/poteto-mode この PR はアイドル時でも 750ms ごとにスクロールがずれる。最初に再現してから、修正と検証をして。
/poteto-mode 仮想化しているのにリスト表示が 1〜2 秒遅い。CPU トレースを取り原因を示して。
/poteto-mode フィーチャーフラグ背後で小さな機能を作成。実際に動くことを確認して。
/poteto-mode markdown レンダラーを2種類作って比較しよう。個別にエージェントを起動して。
/poteto-mode このスキルを OSS として公開して。内部情報は漏らさず、temp ディレクトリで作業し、まず依存関係グラフを見せて。
/poteto-mode 寝る。CI が flake しても stack を着地させろ。朝にはマージ済みであってほしい。
/poteto-mode このフラグがオンのとき行間が高すぎる。2 枚目の画像が正しい。再現して一致するまで修正して。
```

また、必要に応じて他のスキルをオンデマンドで起動することもできる。

- `/how`: サブシステムが実際にどのように動くかを順番に説明してほしいとき
- `/why`: なぜこの設計なのか知りたいとき。利用可能な MCP で、ソース管理・課題トラッカー・設計資料・チャット・監視・エラー追跡・分析基盤の証拠を並列取得
- `/architect`: 関数境界を越えてコードを書く前に型とデータ構造を先に決めたいとき
- `/arena`: 同じ作業を N 本並列で実行し、良い部分を取り込むとき
- `/interrogate`: モデル間でアドバーサリアルにレビューしてほしいとき
- `/tdd`: バグ修正時。まず失敗テストを作成してから修正
- `/unslop`: AI の文章を平易化して、雑さを削るとき
- `/reflect`: 長いやり取り後に継続的改善したいとき
- `/figure-it-out`: 変わった事柄に取り組む際。監査可能で厳密な playbook を設計
- `/show-me-your-work`: レビュー可能な意思決定ログを保存。TSV としてコミットできる

最後に、`/automate-me` で自分専用の mode スキルを作れる。  
最近の会話ログから、あなたの作業スタイルを元に `your-mode` スキルを下書きし、内部では pstack 経由でルーティングする。

pstack はどのエージェント型コーディングツールでも動く。  
ただし、Cursor のようなマルチモデルツールでは特に相性が良い。  
多くのスキルがマルチモデルの特性を活かし、各モデルの強みと弱みを分担して使う。  
これは、幅で拡張する「横並び」のオーケストレーションではなく、深さを重視する設計だ。

エージェントのボトルネックは検証だ。  
エージェントは短時間で大量のコードを書ける。  
しかし、そのすべてが正しいかを担保するのは非常に難しい。  
その難所を越えられれば、ソフトウェアのダークファクトリーに近い真の並列化が成立する可能性がある。

ただしまずは深く、厳密に。  
その先にあるのは「信頼」を上げることだと思う。

`pstack` を試して、感想を聞かせてほしい。

## Zen and the Art of Software Maintenance

これらのスキルは、コードを書く際の自信を高めてくれる。  
ただ、エージェントが大量にコードを書いた現在、保守は悪夢に近い。  
バグ、パフォーマンス問題、機能要望はまだ時間を要するし、件数も増える一方だ。

Cursor でのオートメーションを広く使っている。  
例えばボットの Benny には、pstack の同じスキルを持たせている。  
Cloud Agent が Slack の新規メッセージなどのイベントに反応して起動する例もある。

![Benny の姿](Image)

Benny はまだ進化途中だが、目標はソフトウェア保守フローをできる限り自動化することだ。  
考え方としてはこうだ。  
pstack を使って「最初からほぼ一発で」解決できるという確信が出てくるなら、PR の品質が高いことが十分保証できる範囲に入る。  
ならばフィードバック工程も自動化できるはずだ。

このフローは、最初にトリアージから始まる。  
まず従業員からバグ報告情報を集約する。  
私たちは Cursor の利用者にもフィードバックを集めており、リリース候補への情報も多く届く。  
Benny は画像や動画添付も理解し、コードベースを pstack スキルで探索し、再現手順が不明瞭なときは報告者に追加情報を確認する。

![Benny が追加情報を要求する](Image)

これがバグ報告の重要部分だ。  
再現手順と何が壊れているかが不明瞭だと、解決は推測に依存する。  
どこでどう壊れているかを明確に示す情報が必要だ。

トリアージ後、Benny はチケットを作成する。  
ここではコード、直近の回帰を示す git 履歴、Slack の関連会話、設計・プロダクト判断を載せた Notion の情報まで見て、これはバグか仕様通りかを分類する。

チケット登録が終わると、別の Benny が `/orchestrate` というスキルで引き継ぐ。

> 5 月 8 日  
>  
> `/orchestrate` を導入。  
> Cursor SDK を使い、最も難度の高いタスクに対して再帰的にエージェントを起動するスキルだ。  
> これを使って得た成果:
> - 社内の独自スキルを自動調査し、トークン使用量を 20% 削減しつつ eval を改善
> - 社内バックエンドのコールドスタートを 80% 短縮

まず、コンピュータ上で問題の再現性を確認する。  
Cursor の Cloud Agents は、クラウド上で Cursor 自体を実行し、デスクトップと対話し、クリックやキーボード入力を行う。  
内部的には、CDP などのプロトコルで製品操作をプログラム的に制御するためのスキルをさらに増やしている。

これで、バグ報告が再現できるかを示せる。再現が成立すれば修正試行に進む。  
性能問題なら、修正前後の CPU トレースとヒープスナップショットも取得できる。  
サブプランナーが追加ワーカーを起動して、pstack スキルを使い修正内容を確認し、チケットとの照合も行う。

この実行でも、さらにワーカーが追加され、前後の操作を動画で記録。最後に別ワーカーが PR を開き、説明文に動画を添付してレビューに回す。

![再現できて修正済みの例](Image)

これはまだ進化途中だが、かなりの作業が残っている。  
それでも、寝ている間や他の作業をしている間でも、エージェントのチームでバグ修正の自信を持てるようになるのが楽しみだ。  
コードレビューの拡張性向上も大きなテーマで、Cursor には近く面白い機能追加が来ると思っている。

自分のソフトウェアファクトリーを構築する鍵は「信頼」だ。  
検証を含めて問題を最後まで引き受けられるエージェントを信用できなければ、プロセス自動化は成立しない。  
pstack のようなプラグインでエージェントのエンジニアリングの深度を上げ、信頼を高めれば、より野心的な課題に取り組める。  
まだ信頼していないエージェントをいきなり並列化するのは、トークンを大きく浪費し、より多くのノイズコードを増やすだけだ。

読んでくれてありがとう。
