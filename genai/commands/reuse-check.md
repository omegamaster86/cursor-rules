# 既存コード流用チェック

現在のブランチの変更について、**新規実装・重複定義がないか**を調べ、リポジトリ内の既存コードで置き換え可能なものを列挙し、具体的な修正案を提示してください。

## 実行環境（重要）

- 本コマンドは **コマンドを配置した対象リポジトリ（PJ）** 内だけで完結させる。
- **Fallow MCP・`fallow` CLI・fallow リポジトリの参照は行わない**（PJ に導入されていない想定）。
- 静的解析は **`git diff` / `grep` / `codebase_search` / `Read`** のみ。PJ に `.fallowrc.json` / `fallow.toml` がある場合は、**境界・ignore 設定を読むだけ**（バイナリ実行はしない）。

## 前提

- ベースブランチは未指定なら、リポジトリのデフォルトブランチ（多くは `main` または `master`）。会話で別ブランチが指定されていればそれを使う。
- 読み取りの調査まで行う。**修正の自動適用・コミットはしない**（修正案は提示のみ）。
- UI/UX のデザイン変更提案はしない（型・util・API・ロジックの共通化のみ）。
- **構造チェック（事実）** と **Must/Should（意味的な流用判断）** は別軸。両方をレポートに含める。

## Step 0: リポジトリ構造の把握（短く）

差分を見る前に、当該リポジトリで次を把握する（README、`package.json`、`tsconfig` paths、ディレクトリ一覧、`.cursor/rules`、**`.fallowrc.json` / `fallow.toml` の `boundaries` があれば**）:

- 型・定数の置き場（例: `types/`, `@/types`, `shared/`, `lib/`）
- 共通 util / helper の置き場
- API クライアント・サービス層の置き場と命名規則
- 複数チャネル（Web/API/CLI/バッチ等）やロール別の並行実装があるか
- レイヤー境界（規約ドキュメントまたは fallow 設定の zones / rules）

## Step 1: 差分の取得と分類

```bash
git fetch origin <base-branch> 2>/dev/null || true
git diff origin/<base-branch>...HEAD --stat
git diff origin/<base-branch>...HEAD
```

変更ファイルを分類する:

| 優先 | 種別 | 例 |
|------|------|-----|
| 高 | 新規型・定数・ユニオン | `type`, `interface`, `enum`, `as const`, 文字列リテラル union |
| 高 | 新規ユーティリティ | `format*`, `parse*`, `build*`, `merge*`, `validate*`, `map*` |
| 高 | 新規 API / データアクセス | `fetch`, `client`, `repository`, `service`, `api/` |
| 中 | 新規 UI / コンポーネント | コンポーネント・ビュー・テンプレート |
| 中 | 設定・スキーマ | Zod schema, OpenAPI, migration 以外の重複定義 |
| 低 | スタイルのみ | 流用観点からは除外 |

## Step 1.5: 構造チェック（変更差分のみ・手動）

Step 1 で追加・変更されたファイル・シンボルに限定し、次を確認する（**今回の差分で新たに疑わしいもの**を優先。リポジトリ全体の既存負債の総点検はしない）。

| 観点 | 手順（PJ 内のみ） |
|------|-------------------|
| 同名・二重 export | 差分の `export` 名を `grep` で全体検索。2 箇所以上なら **Must 流用**候補 |
| 未参照の新規 export | 各 export 名の import を `grep`。0 件なら削除 or 流用先再検討 |
| 類似ブロック（クローン） | 差分の関数・ロジック塊の特徴（関数名・リテラル・コメント）で `grep` / `codebase_search` |
| 未宣言依存 | 差分の `import` パッケージが `package.json` の `dependencies` / `devDependencies` にあるか `Read` |
| 解決不能 import | 相対パス・エイリアスが `tsconfig` paths と整合するか、対象ファイルが存在するか |
| レイヤー違反 | 変更ファイルの import 先が、Step 0 の境界・Next.js ディレクトリ規約と矛盾しないか |
| barrel 循環の疑い | 変更が `index.ts` 再 export なら、import チェーンを 2〜3 ホップ `Read` で確認 |

結果は Step 2 の入力とする。件数は「差分由来で新規に疑わしい件数」と明記する。

## Step 2: 重複・流用候補の探索

差分で**追加・変更された**シンボル名・定数名・ドメイン用語・リテラル値ごとに:

1. **構造チェックの反映**: Step 1.5 の二重 export・クローン候補・未参照 export を先にマッピング
2. **完全一致**: シンボル名・定数名・リテラルでリポジトリ全体を検索
3. **意味的に近い実装**: `codebase_search`（変更の意図・ドメイン語で検索）
4. **型・定数の一元管理**: Step 0 で把握した型置き場に同等の union / 定数がないか
5. **チャネル・出力形式のペア**: 同じドメインロジックが別レイヤに既にないか
6. **ロール・コンテキストのペア**: 似た権限・画面向けの実装が別パスに既にないか
7. **既存の利用例**: 流用候補の import を `grep` で 1〜2 件確認（barrel 経由も追う）

プロジェクト内ドキュメント（`README`, `docs/`, `.cursor/` 配下）があれば、ドメイン用語の意味づけに参照する。

## Step 3: 流用可否の判定

| 判定 | 条件 |
|------|------|
| **Must 流用** | 既存の型・定数・util と意味が重複し、差分が二重定義。Step 1.5 で同名 export や実質同一クローンが見つかった場合を含む |
| **Should 流用** | 既存モジュールを import / 呼び出すだけで同等動作になる |
| **検討** | 類似だが引数・コンテキスト・依存が異なる（共通化は別 PR と明記） |
| **新規で OK** | 既存検索で同等物なし、かつスコープ内で新規が妥当（YAGNI） |

早すぎる共通化は避ける。1 箇所専用のロジックを、根拠なく shared に上げない。

## Step 4: 出力フォーマット（必ずこの形式）

```markdown
## 既存コード流用チェック

### 差分サマリ
- ベース: `<branch>`
- 変更ファイル数: N
- 重点領域: [変更の要約を 1 行]

### 構造チェックサマリ（差分スコープ）
- 二重 export: N 件
- クローン候補: N 件
- 未参照の新規 export: N 件
- 依存・import 異常: N 件
- 主要 finding（path:line — 観点 — 1 行）— 上位 5 件まで

### 流用推奨（Must / Should）

#### 1. [短いタイトル]
- **変更箇所**: `path/to/file` Lxx–Lyy
- **問題**: [重複定義 / 既存と別名の同等型 など]
- **根拠**: 構造チェック | grep | codebase_search
- **既存の流用先**: `path/to/existing` の `SymbolName`
- **参照例**: [既に使っているファイル 1–2 件]
- **修正案**:
  ```言語
  // Before（差分の要約）
  // After（import・型・定数・呼び出しの置き換え）
  ```

### 任意・別 PR
- [検討レベルの項目]

### 新規実装で問題なし
- [理由付きで OK なもの]

### 探索ログ（簡潔）
- git / grep パターン / codebase_search クエリ（再現用）
```

## 注意

- 「似ているから統合」は **ファイルパス・シンボル名・既存利用箇所** を根拠にすること。曖昧な場合は **検討** に落とす。
- セキュリティ・コーディング規約の総合レビューは本コマンドの範囲外。必要なら別コマンドやレビュー skill で確認する。
- PJ で後から Fallow を CI 導入する場合も、本コマンドの手順はそのまま有効（ローカルで Fallow を回すのは開発者任意。コマンド本文からは要求しない）。
