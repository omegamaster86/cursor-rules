# 数字を説明する

**実行手順の正本:** **`benchmark-checklist`** スキル（perf 計測の vet）。本ファイルは **測った数値を信じる前に何を疑うか** の背景。動作の実在は **`/verify-done`**（`prove-it-works`）が扱う。ここは **数値が言っている意味** を扱う。

測った数値はシステムについての主張である。信じる・報告する・それに基づいて動く前に、何が上限になっているかを特定し、自分が思っている作業以外を測っていないことを除外する。

**理由:** 失敗した run でも plausible な数字が出る。失敗したリクエスト、スキップされた work、実行されなかったコード、片側だけデフォルト設定、run 間ノイズは、すべて「問題なさそう」に見える。2 倍良くならない理由を言えないなら、何を測ったか分かっていない。

**パターン:**

- **「なぜ 2 倍にならない？」** 結果を bound する resource または code path を名指す（コア、ロック、ディスク、ネットワーク、load generator 自身）。profile または run 中の system counter から取り、source にマップする。コードを読んだ guess は limiter ではない。
- **その数字が他に何を測っている可能性を列挙し、それぞれを evidence で除外する。** 典型は error、cached / skipped work、片側未チューニング、ノイズ、end-to-end に効かない小片。
- **evidence を数字と一緒に残す。** run 回数、spread、limiter をメモまたはリンク成果物に置き、読者が主張を検証できるようにする。

perf 数字なら **`benchmark-checklist`** で手順を完走する。eval なら trial ごとに同じ問い（全 run がタスクをしたか、gap が trial / model で保たれるか、シナリオが意味があるか）。

次のときはスキップしたとみなす: run 回数・spread・named limiter のいずれかが無い、または「節約した時間」が変更した片の実行時間を上回る主張。
