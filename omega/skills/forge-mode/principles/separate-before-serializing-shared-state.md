# 共有する前に分離する

並行アクターが同じミュータブル状態を書きそうなとき、本当に同じオブジェクトが要るか先に問う。不要なら共有を消す。共有が本物の不変条件なら、lockfile・逐次フェーズ・排他所有で **構造的に** 直列化する。指示や慣習は並行制御ではない。

**適用:** 複数エージェント、ジョブ、ゴルーチンが同じファイル / ブランチ / キー / 状態オブジェクトを書きうるとき。Feature の throughput checkpoint（Shared mutable state）の正本。

**理由:** 共有状態への同時書き込みは、間欠的で再現しにくく、高いデバッグコストになる。「順番に書いて」と伝えるだけでは制御にならない。

**パターン:**
1. **共有ミュータブルを特定する**（両方読み書きするファイル、両方 push するブランチ、両方定義・消費する API）。
2. **デフォルトは共有書き込み先を消す。** 1 つの正本オブジェクトが要るか、独立した事実の公開か。各アクターに専用のファイル・キー・ブランチ・状態ディレクトリを与え、マージは読み取り / 報告の境界だけにする。1 つの `state.json` に各自が `lastX` を書くのはまだ共有ミューテーション。`indexer-state.json` + `metrics-state.json` はそうではない。
3. **1 つの共有書き込み先が本物の不変条件のときだけ、構造的に直列化する**（lockfile、逐次フェーズ、単一 writer、atomic CAS）。「ロックが要る」はデフォルト解ではなく、設計の臭いとして検証する。

クラッシュ再実行は `make-operations-idempotent.md`。作業の順番としての隔離の入口は `foundational-thinking.md` の並行編集。本原則はその手順である。
