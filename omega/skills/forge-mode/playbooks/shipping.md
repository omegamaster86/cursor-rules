### Shipping

**land するものを自分が持つ。各 PR を独立に verify し、root からの verified run だけ land し、その後 stack に手を出さない。**

1. **forge を resolve し、land 前に各 PR を独立に verify。** GitHub CLI（`gh`）が default。`command -v origin` が成功し Origin が repo を解決できるなら PR 操作はすべて `origin pr ...`。なければ `gh` に留まり fallback を記録。Graphite（`gt`）は要求しない。PR あたり 1 verifier、各々 Cursor cloud agent。matching control skill（`cursor-team-kit` の `control-ui` や `control-cli` 等）でユーザーと同じように parent vs head で変更を走らせ、`PASS`、`PASS+NOTES`、`FAIL` をその PR に post。コードを書かなかった agent からの verdict だけが有効。作者は「意図したものを作ったか」を確認する。green CI と approving bot review は verdict ではない。
2. **bottom で root した contiguous verified run だけ land。** 最下 unmerged PR から上へ歩き、`PASS` か `PASS+NOTES` のない最初の PR で stop。その下が run、上端が ceiling。unverified の下に verified PR があっても、その下の code が無いので land できない。branch がその code を持たず要らない PR は trunk に載せて単独 land できるが、fresh verdict が要る。古い verdict は下にその code があった状態で走ったため。
3. **verdict がまだ code を述べているか再確認。** verdict は patch を覆う。chain rebase は check を fail せず上の PR を新 SHA に動かす。古い verdict を信じる前に verdict SHA と current head で `git patch-id` を比較。差が tests、docs、lint config だけなら、両 SHA で同じものを build でき noise 以外同じなら lane 結果は有効。noise は verdict SHA の 2 build 間にも出る差、または埋め込み commit SHA。各 noise の種類と file を report し読者が判断できるようにする。変更本体は fresh check と review が要る。lane に build 出力が無い（dev server 等）なら rerun。他に drift があれば re-verify。
4. **bottom-up で 1 PR ずつ land。** run の最下 unmerged PR を `origin pr merge <pr>` か `gh pr merge <pr> --squash` で merge。Origin の plain merge は指定 PR より下も merge する。GitHub で base が親 branch の PR は trunk ではなくその branch に merge される。結果は `origin pr view <pr>` か `gh pr view <pr> --json state,mergedAt,baseRefName` で読み戻す。merge queue が queued しただけで成功に見えることがある。auto-merge 要求は merge ではない。land 済み PR は base が trunk で merged と読める。`--auto`（Origin merge-when-ready か GitHub auto-merge）は current head を覆う verdict がある PR だけ。merge 後、親 branch が base だった次 PR を trunk に retarget（`origin pr edit <pr> --base <trunk>` か `gh pr edit`）、patch を merge 結果に載せ `--force-with-lease` で push。verdict は patch を覆う。step 3 の patch-id rule が verdict の生存を決める。check が pass し verdict が生きていれば merge。
5. **land 中は stack を触らない。** step 4 の次 PR の移動だけが branch / base の変更。merge はその瞬間の branch と base を land する。GitHub では `playbooks/babysit.md` の queued watcher（`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>`）を `/loop` で ceiling の `COMPLETE` まで。Origin では `origin pr checks <pr> --watch` の各 return で `origin pr view <pr> --checks` を読み ceiling が merged になるまで。親 merge で base が trunk に動くのは想定内。stall したら mutate 前に理由を調べる。
6. **ceiling で stop。** run を延ばすには新 verdict が要り、step 1 の新 pass になる。

**Reply:** verified run と ceiling、各 PR の verdict と producer、land したものと確認方法、次の gap に要るもの。
