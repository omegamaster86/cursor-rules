# Ketchup

ユーザーが `/ketchup` の直前に書いた最後のメッセージ以降、このチャットで起きたことをキャッチアップし、各変化の「今どこまでか」だけでなく「何が変わったか」も伝える。そのあと、ユーザーだけが取れる判断を、返信だけで決められる形で並べる。通知とサブエージェント結果はユーザーのメッセージではない。ユーザーは自分の最後のメッセージだけ覚えていて、その後は何も知らないと仮定する。

[`/bro`](../bro/SKILL.md) の声を使い、その restating タスクはしない。平易な言葉、短い文、専門用語なし。ユーザーにとって何が変わったかを書き、どうやったかは書かない。「CI は green」ではなく「テストは通った」と言う。ユーザーが動くために必要なとき以外は hash、パス、コマンド、ビルド番号、テスト件数は省く。PR・branch・エージェントは作業中に付けたラベルではなく、ユーザーが知っている名前で呼ぶ。文脈がないと意味が通じない事実は文脈を付けるか、その事実ごと省く。

## 何が変わったか集める

このターンは read-only。ビジュアルは既にあるものだけから作る。コードを変え、アプリやジョブを起動し、何かを post しない。そのメッセージ以降の自分の作業、サブエージェントの報告、このチャットの他者メッセージを集める。このチャットが触れた各 PR・CI・エージェントの現状を確認する。示す数字は根拠と照合し、直したときはそう言う。

action item はユーザーだけが取れる決定またはステップ（プロダクト判断、承認、不可逆操作、アクセス不足）。ユーザー最後のメッセージより前から待っているものも含める。自分がまだできる作業は action item ではない。返信を埋めるための判断を捏造しない。ユーザーが求めておらず作業にも不要なステップは action item ではない。不可逆でユーザー待ちのものだけは action item 1 行（ビジュアルなし）。

1 つの call が複数 item をまとめられる（merge 待ちの PR セットなど）。各 item について link、ユーザーにとっての変化、推奨の根拠となる evidence、risk、推奨（pick）を集める。call に必要な事実が分からなければ `unknown` と書く。link が無ければ省く。

## 返信を書く

語数は call に使う。起きたことは短く（図を除き 100 語以内、少なければさらに短く）。ユーザーに変化がなかった作業は省く。各 item にはだいたい 30 語。item が 2 つなら全体は 150 語を大きく下回り、30 つならずっと長くなる。語数制限のために item を削ったり縮めたりしない。リストの代わりに件数だけ、item の代わりに link だけは禁止。link は補足に使えるが、返信単体で決められることが前提。

冒頭 1 文でユーザー判断が要ることを述べる（無ければそう言う）。action item が詳細。何も起きておらずユーザー待ちもなければそう言って終える。

次に起きたことを示す。ビジュアルを先に。スクリーンショットと動画を埋め込み、変化を説明する図があれば続ける。ユーザーが求めたことごとに 1 短い bullet：何になったか、完了・実行中・失敗・未確認か。声に出して言う形（「検索が index 不足で遅かった」、タグだけの行は不可）。途中で見つけて直したバグは名指す。各行は単独で真実。ユーザー待ちのものを完了扱いにしない。要約の下に、ユーザーの知識や行動を変える行を最大 3 行。自分がまだできる残作業を 1 行。

action item を列挙する。ユーザーが持つ call（merge、approve、選択）を聞き、推奨を述べる。自分が先に取るステップ、先に必要なこと、不可逆なことは推奨に含める。PR・issue・エージェントの番号や link を call の中でも options の間でも示す。

call の形に合わせる。1 item だけなら 1 bullet：call、推奨、ユーザーへの変化、evidence、risk（item 名は 1 回だけ）。複数 item が同じ call なら call と推奨は 1 回、各 item は別 bullet（risk が高い順）：link と名前、変化、evidence、risk。item ごとの推奨が call と違うときだけ item 側に書く。risk は低くても書く（例：「Low risk: 色だけ変わる」）。待つコストは、遅れ以上のもの（締切、データ損失など）のときだけ述べる。

選択肢の call では、検討した全 option を載せ、各 gain と cost、状態があれば現状を書く。cost が call の risk なので別 risk 行は不要。上のスクリーンショットが option を示しているなら、各画像の下に gain と cost を書く。

## ビジュアル

ビジュアルはスクリーンショット、動画、Mermaid 図、`/visualize` のチャート、生成画像。Markdown 表はビジュアルではない（before/after 列があっても）。

文より図の方が伝わるときは描く：設計やシステムの仕組み、PR stack（各 PR の状態）、修正の before/after、選択肢の並列。状態リスト、action item リスト、つながりのない箱は描かない。テキストでもビジュアル間でも同じ事実を二度書かない。

各ビジュアルは一目で読める大きさ。箱は最大 6、各ラベルは口に出す言葉で最大 8 語。「Tests: pass」のようなタグは使わない。文が要る事実は本文に書くか書かない。

画面に見える変化はリンクだけでなくインラインで埋め込む。見える変化なのにキャプチャが無い行は「No screenshot yet,」と書き、画面上何が変わったかを言う。持っている事実から Mermaid や `/visualize` を描く。数字を捏造しない。キャプチャしていない画面の絵を描いたり生成したりしない。存在する成果物だけリンクする。
