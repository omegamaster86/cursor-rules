# Study Log

チャットで扱った **意味・文法・挙動** の理解を、テックブログ記事のように詳細かつわかりやすく `.cursor/study-log/` に残す。

## いつ使うか

- ユーザーが「study-log に書いて」「学習ログにまとめて」などと明示したとき
- 意味・文法・挙動の説明が主で、あとから読み返せる記事にしたいとき
- セッション作業メモ（進捗・検証・次の一手）は対象外 → `session-log` 側

## 手順

1. **出力先を確保する**
   - パス: `.cursor/study-log/`（プロジェクトルート相対）
   - フォルダがなければ作成する

2. **トピックを抽出する**
   - チャットから「これってどういう意味 / 文法 / 挙動」系の Qu を中心にまとめる
   - 実装タスクの進捗や TODO は書かない（必要なら別途 session-log）
   - 1 ファイル = 1 トピック（複数トピックならファイルを分ける）

3. **ファイルを新規作成する**
   - 既存ファイルへの追記はしない（常に新規）
   - ファイル名: `YYYY-MM-DD-<slug>.md`
   - slug はトピックを英語ケバブケースで短く（例: `useeffectevent-vs-usecallback`）
   - 同日・同 slug が既にあれば `-2` などを付けて衝突を避ける

4. **テックブログ形式で書く**（下記テンプレート）
   - 読者がチャット文脈を知らなくても理解できること
   - 「結論 → なぜ → どう動く → つまずきポイント → まとめ」の流れ
   - コードは最小限・必要箇所のみ。長いダンプ禁止
   - 専門用語は初出で一言説明する

5. **完了報告**
   - 作成したファイルパスをユーザーに伝える
   - 記事のタイトル（H1）を一行で示す

## 記事テンプレート

```markdown
# <わかりやすいタイトル>

作成日: YYYY-MM-DD
タグ: <意味 | 文法 | 挙動>（複数可）

## はじめに

この記事でわかること（1〜3 行）。どんな疑問から来たか。

## 結論（先に答え）

質問への答えを 2〜5 行で先に書く。

## 背景・前提

読者が知っておくとよい前提（言語/フレームワーク/対象コードの位置づけ）。

## 詳しく見る

### <概念や構文の意味>

「〇〇とは何か」を平易な言葉で。たとえ話は 1 つまで。

### <文法・書き方>

構文の読み方、よくある書き方、似た表現との違い。

### <実際の挙動>

いつ走り、何が起き、何が起きないか。タイミング・順序・副作用。

## 具体例

短いコード例 + 「このとき何が起きるか」の解説。

## つまずきやすいポイント

誤解しやすい点、紛らわしい用語、よくあるバグとの関係。

## まとめ

要点を箇条書き 3〜5 個。

## 参照

- 関連ファイル / 公式ドキュメント / チャットで触れた箇所（あれば）
```

セクションはトピックに合わせて省略・統合してよい。ただし **結論を先に置く** ことと **意味 / 文法 / 挙動のどれを扱ったかが分かる** ことは必須。

## 文体

- 日本語で書く
- テックブログ向け: 丁寧すぎず、講義調になりすぎず、読み物として通る文章
- 「〜だと思います」などの曖昧さを避け、断定できることは断定する
- チャットの生ログや Q&A のコピペはしない。再構成して記事にする

## やらないこと

- `.cursor/session-log/` への書き込み（用途が違う）
- UI/UX やプロダクト仕様の変更記録（実装ログではない）
- 機密・トークン・個人情報の記載
- 既存 study-log の無断上書き
