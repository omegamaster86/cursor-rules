# 意思決定ログ

人が事後にレビューする作業では、決定証跡があれば、作業を再実行したり全トランスクリプトを読まずに、何が決まり、なぜ決まったかを再構成できる。正規ログを 1 つ保ち、証跡を一貫させ、将来のエージェントが見つけられるようにする。

## 保存先（Notion）

決定は **Notion データベース** に保存する。接続情報は `.cursor/decision-log/notion.json` を正とする。

| 項目 | 値 |
|------|-----|
| DB 名 | Frontend 意思決定ログ |
| DB URL | https://app.notion.com/p/4fe3f493db19421db81be4715e49fbc5 |
| data_source_id | `04d20aa1-bb32-4847-8628-11fb1570be62` |
| 親ページ | https://app.notion.com/p/21fcdf5b89cb803fb65ed171dca61ae4（日テレ） |

**書き込み**: Notion MCP の `notion-create-pages` を使う。`parent.data_source_id` に上記 ID を指定し、**決定ごとに 1 ページ**を新規作成する（追記のみ。既存ページは編集・削除しない）。

## 形式

各エントリ（Notion ページ 1 件）は次の項目を持つ。

- **決定日** — `YYYY-MM-DD`（プロパティ `決定日`）
- **Name** — 決定の要約（1 行。プロパティ `Name`）
- **決定詳細** — 何をしたか・何に決めたか（ページ本文 `### 決定詳細`）
- **決定理由** — その変更に至った**原因・課題・背景**（ページ本文 `### 決定理由`）

**決定詳細と決定理由の分け方**

| 項目 | 書くこと | 書かないこと |
|------|----------|--------------|
| 決定詳細 | 実施した変更・選んだ方針 | なぜそうしたかの説明 |
| 決定理由 | 困っていたこと、起きていた現象、制約、トレードオフ、なぜそうしたかの説明 | 「ユーザーが依頼したため」だけ |

### ページ作成例（notion-create-pages）

```json
{
  "parent": { "data_source_id": "04d20aa1-bb32-4847-8628-11fb1570be62" },
  "pages": [
    {
      "properties": {
        "Name": "得点比較チャートの横軸刻みを 10 点刻みに変更",
        "date:決定日:start": "2026-05-24",
        "date:決定日:is_datetime": 0
      },
      "content": "### 決定詳細\n得点比較チャートの横軸刻みを、最大得点 11 点以上のとき 5 点刻みから 10 点刻みに変更した\n\n### 決定理由\n5 点刻みだと目盛りが多く、チャート幅が狭い画面ではラベルが詰まって読みにくかった。刻みを粗くして軸を見やすくする必要があった"
    }
  ]
}
```

## エントリをログする

各エントリは同僚に何をしたか伝えるように書く。平易な言葉、具体的行動、AI 口調や抽象ジャーゴンなし。**決定理由は依頼の転記にしない。** 現象・課題・制約から「だからこの変更にした」と読める文にする。

各決定は Notion に **新規ページ 1 件**として追加する。`決定日` は当日の日付を使う。

決定点とチェックポイントをログし、すべての行動ではない: 選んだ分岐、検証結果付き完了ユニット、トリガー付きピボット/リバート、表面化したブロッカー、修正したゲート。ループ実行では反復ごとに 1 ページ。自明・些細はスキップ。

## ルール

- 1 ページは 1 決定またはチェックポイント。1 ページに収まらないなら決定がまだ鮮明でない。
- 追記のみ。誤りは訂正ページを新規作成。履歴を編集・削除しない。
- 形式は上記に従う。

## トランスクリプトに対してログを監査する

実行終了時、返す前にログが真実を語ったか確認。この実行のトランスクリプトをアクティブワークスペースの `agent-transcripts/`（システムプロンプトがパスを名指す）で読む。`~/.cursor/projects/*/` を glob しない。無関係な非公開チャットを読む。実際に起きたことと Notion に作成したページを照合:

- 各ページは実際の行動に対応。捏造・願望的エントリは作らない（作ってしまった場合は訂正ページで補足）。
- 作業を形作ったがログにない分岐・ピボット・放棄アプローチはギャップ。追加する。
- パディングを落とす。誰も監査しないエントリは居場所を稼がない。

物語ではなくログを直す。作業がページの主張とずれたら、ページが間違い。

## 証跡のクロスモデルレビュー（任意）

**デフォルトでは実施しない。** ユーザーが明示的に依頼したときだけ、作業をしたモデルと別モデルファミリのサブエージェントを起動する。

依頼の例: 「クロスレビューして」「クロスモデルレビューお願い」「別モデルでレビューして」

起動した場合の目的: 自己レビューは代替にならない。自分では持てない新鮮な目で、ログとトランスクリプトを読み、ユーザーが注意すべきことを旗立てる。作業のやり直しではなく、最適でない・リスクのあるもののスキャン。

- 決定詳細と実際の変更・行動のずれ
- スキップまたはトランスクリプトに証明なく主張された検証ステップ
- 後知恵でリスクに見える選択（時期尚早、スコープ肥大、症状のごまかし）
- ざっと読むと見逃すギャップ

クロスレビューを実施した返答だけ、末尾に "Attention" 節を付ける。レビュアーのモデルを単独行で先頭に（`reviewed by <model>`）、各フラグは特定ページまたは瞬間を指す。「No flags」は有効。モデル名だけは不可。

クロスレビューなしの通常の `/decision-log` では、作成した Notion ページの URL と主要な決定の要約を返せばよい。Attention 節は不要。

## 証跡のレビュー

Notion DB を上から下へ読み、決定詳細とコード・成果物を照合してスポットチェック。未検証の主張やログにない重要な分岐は監査がギャップを捕まえた。

## このスキルの合成

他スキルは独自を作らず監査証跡をここにルーティング。名前で参照し、形式はここが所有。3 項目（決定日・決定詳細・決定理由）を言い換えない。
