はじめに
スキルは、Claude に特定のタスクやワークフローの処理方法を教える一連の指示 (単純なフォルダーとしてパッケージ化) です。
スキルは、特定のニーズに合わせて Claude をカスタマイズする最も強力な方法の 1 つです。
会話のたびに自分の好み、プロセス、専門知識を再度説明する代わりに、スキルを一度 Claude に教えれば、毎回その恩恵を受けることができます。
仕様からフロントエンド設計を生成する、一貫した方法論で調査を実施する、チームのスタイルガイドに従ったドキュメントを作成する、
複数ステップのプロセスを調整するなど、反復可能なワークフローがある場合、スキルは強力です。
これらは、コード実行やドキュメント作成などの Claude の組み込み機能とうまく連携します。 
MCP 統合を構築しているユーザーにとって、スキルは、生のツールへのアクセスを信頼性の高い、最適化されたワークフローに変える強力なレイヤーをさらに追加します。
このガイドでは、計画から構造、テスト、配布まで、効果的なスキルを構築するために知っておくべきすべてのことをカバーしています。
自分自身、チーム、コミュニティのためのスキルを構築する場合でも、実用的なパターンと実際の例が随所に見つかります。
学べること:
• 技術的要件とスキル構造のベストプラクティス
• スタンドアロン スキルと MCP で強化されたワークフローのパターン
• さまざまなユースケースで有効だった実践パターン
• スキルをテスト、反復、配布する方法
対象者:
• Claude に特定のワークフローを一貫して実行させたい開発者
• Claude に特定のワークフローに従ってもらいたいパワー ユーザー
• 組織全体で Claude の働き方を標準化したいと考えているチーム
このガイドの読み方（2つの進め方）
スタンドアロンのスキルを構築する場合は、基礎、企画・設計、およびカテゴリ 1 ～ 2 に焦点を当てます。 MCP 統合を強化する場合は、「スキル + MCP」セクションとカテゴリ 3 はあなたのためのものです。どちらのパスも同じ技術要件を共有しますが、ユースケースに関連するものを選択してください。このガイドで身につくこと: 最後までに、一度で機能的なスキルを構築できるようになります。 skill-creator を使用して最初の実用的なスキルを構築してテストするには、約 15 ～ 30 分かかると予想されます。始めましょう。

第1章
基礎
スキルとは何ですか?
スキルは、以下を含むフォルダーです。
• SKILL.md (必須): YAML フロントマターを使用した Markdown の命令
• scripts/ (オプション): 実行可能コード (Python、Bash など)
• references/ (オプション): 必要に応じてロードされるドキュメント
• assets/ (オプション): 出力で使用されるテンプレート、フォント、アイコン
核となる設計原則
漸進的開示
スキルには 3 つのレベル システムが使用されます。
• 第 1 レベル (YAML フロントマター): 常にClaudeのシステム プロンプトにロードされます。
すべてのスキルをコンテキストにロードすることなく、Claude が各スキルをいつ使用する必要があるかを知るのに十分な情報を提供します。
• 第 2 レベル (SKILL.md 本体): Claude がスキルを認識したときにロードされます。
現在のタスクに関連するもの。完全な手順とガイダンスが含まれています。
• 第 3 レベル (リンクされたファイル): スキル ディレクトリ内にバンドルされた追加ファイル
Claude は、必要な場合にのみナビゲートして発見することを選択できます。この段階的な開示により、専門知識を維持しながらトークンの使用量が最小限に抑えられます。
構成可能性
Claude は複数のスキルを同時にロードできます。私たちのスキルは、それが利用可能な唯一の能力であると想定するのではなく、他のスキルと併用してうまく機能する必要があります。
移植性
スキルは、Claude.ai、Claude Code、API 全体で同様に機能します。スキルを一度作成すると、環境がスキルに必要な依存関係をサポートしていれば、変更することなくすべての環境で機能します。
MCP ビルダー向け: スキル + コネクタ
💡 MCP なしでスタンドアロンのスキルを構築しますか? 「企画・設計」にスキップします。後でいつでもここに戻ることができます。すでに動作する MCP サーバーがある場合は、難しい部分は完了です。スキルは最上位の知識層であり、すでに知っているワークフローとベスト プラクティスを取り込むため、Claude はそれらを一貫して適用できます。
キッチンの例え
MCP は、プロ仕様のキッチン、つまりツール、食材、設備へのアクセスを提供します。スキルはレシピを提供します。つまり、価値のあるものを作成する方法についての段階的な指示です。

MCPユーザーにとって重要な理由
スキルなし:
• ユーザーは MCP に接続したが、次に何をすればよいかわからない
• 「統合で X を行うにはどうすればよいですか」というサポート チケット
• 各会話はゼロから始まります
• ユーザーが毎回異なるプロンプトを表示するため、結果が一貫しない
• 本当の問題はワークフローのガイダンスにあるのに、ユーザーはコネクタを責める
スキル付き:
• 事前に構築されたワークフローは、必要に応じて自動的にアクティブ化されます
• 一貫した信頼性の高いツールの使用
• すべてのインタラクションに組み込まれたベストプラクティス
• 統合の学習曲線を短縮する

企画・設計
ユースケースから始める
コードを記述する前に、スキルで有効にする必要がある具体的なユースケースを 2 ～ 3 つ特定してください。
良いユースケースの定義:
ユースケース: プロジェクトのスプリント計画
トリガー: ユーザーが「このスプリントの計画を手伝ってください」または「作成してください」と言った場合
スプリントタスク」
手順:
1. Linear から現在のプロジェクトのステータスを取得します (MCP 経由)
2. チームの速度と能力を分析します
3. タスクの優先順位を提案します
4. 適切なラベルと見積もりを使用して Linear でタスクを作成します
結果: タスクが作成された完全に計画されたスプリント
自分自身に問いかけてください:
• ユーザーが達成したいことは何ですか?
• これにはどのような複数ステップのワークフローが必要ですか?
• どのツールが必要ですか (内蔵または MCP?)
• どのようなドメイン知識やベストプラクティスを組み込む必要がありますか?
一般的なスキルのユースケースのカテゴリ
Anthropic では、次の 3 つの一般的な使用例を観察しました。
カテゴリ1: ドキュメント/アセット作成
用途: ドキュメント、プレゼンテーション、アプリ、デザイン、コードなど、一貫性のある高品質の出力の作成。実際の例: フロントエンド設計スキル (docx、pptx、xlsx、および ppt のスキルも参照) 「高い設計品質を備えた、特徴的な運用グレードのフロントエンド インターフェイスを作成します。Web コンポーネント、ページ、成果物、ポスター、またはアプリケーションを構築するときに使用します。」
主なテクニック:
• 埋め込みスタイルガイドとブランド標準
• 一貫した出力のためのテンプレート構造
• 最終仕上げ前の品質チェックリスト
• 外部ツールは不要 - Claude の組み込み機能を使用します

用途: 複数の MCP サーバー間の調整を含む、一貫した方法論の恩恵を受ける複数ステップのプロセス。実際の例: スキルクリエイタースキル

主なテクニック:

• 一般的な構造のテンプレート
• 組み込みのレビューと改善提案
• 反復改良ループ
カテゴリ3: MCP強化
用途: MCP サーバーが提供するツールへのアクセスを強化するためのワークフロー ガイダンス。実際の例: Sentry-code-review スキル (Sentry より) 「MCP サーバー経由の Sentry のエラー監視データを使用して、GitHub プル リクエストで検出されたバグを自動的に分析して修正します。」
主なテクニック:
• 複数の MCP コールを順番に調整します。
• ドメインの専門知識を埋め込む
• ユーザーが指定する必要があるコンテキストを提供します。
• 一般的な MCP 問題のエラー処理
成功基準を定義する
自分のスキルが機能していることをどうやって確認できますか? これらは野心的な目標であり、正確なしきい値ではなく大まかなベンチマークです。厳密さを目指しますが、雰囲気に基づく評価の要素があることを受け入れてください。私たちは、より堅牢な測定ガイダンスとツールを積極的に開発しています。定量的指標:
• 関連するクエリの 90% でスキルがトリガーされる
– 測定方法: スキルをトリガーするテスト クエリを 10 ～ 20 回実行します。自動的にロードされる回数と明示的な呼び出しが必要な回数を追跡します。
• X ツール呼び出しでワークフローを完了する
– 測定方法: スキルを有効にした場合と無効にした場合で同じタスクを比較します。ツールの呼び出しと消費されたトークンの合計をカウントします。
• ワークフローごとに失敗した API 呼び出しは 0 件
– 測定方法: テスト実行中に MCP サーバーのログを監視します。再試行率とエラー コードを追跡します。定性的指標:
• ユーザーは次のステップについてClaude に確認する必要がありません。
– 評価方法: テスト中に、リダイレクトまたは明確化する必要がある頻度に注意してください。ベータ版ユーザーにフィードバックを求めます。
• ワークフローはユーザーによる修正なしで完了します
– 評価方法: 同じリクエストを 3 ～ 5 回実行します。出力を比較して、構造の一貫性と品質を確認します。
• セッション全体で一貫した結果
– 評価方法: 新しいユーザーは、最小限のガイダンスで最初の試行でタスクを完了できますか? 9

重要なルール
SKILL.md の命名:
• SKILL.md と一致する必要があります (大文字と小文字が区別されます)。
• バリエーションは受け入れられません (SKILL.MD、skill.md など)。
スキルフォルダー名:
• kebab-case を使用します: notion-project-setup ✅
• スペースなし: Notion プロジェクトのセットアップ ❌
• アンダースコアなし: notion_project_setup ❌
• 大文字なし: NotionProjectSetup ❌
README.md について:
• スキルフォルダー内に README.md を含めないでください。
• すべてのドキュメントは SKILL.md またはreferences/ に格納されます。
• 注: GitHub 経由で配布する場合でも、リポジトリレベルの README が必要になります。
詳細は「配布と共有」章を参照してください。
YAML のフロントマター: 最も重要な部分
YAMLフロントマターは、Claude がスキルをロードするかどうかをどのように決定するかです。これを正しく理解してください。
最低限必要なフォーマット
---
名前: あなたのスキル名
説明: 何をするのか。ユーザーが[特定のフレーズ]を要求する場合に使用します。 --- 始める必要があるのはこれだけです。
フィールド要件
名前 (必須):
• ケバブケースのみ
• スペースや大文字は使用できません
• フォルダー名と一致する必要があります
説明 (必須):
• 次の両方を含める必要があります。
– スキルの内容 – いつ使用するか（発動条件）
• 1024 文字未満
• XML タグ (< または >) なし
• ユーザーが言いそうな具体的なタスクを含める
• 関連する場合はファイルの種類について言及する

テストと反復
ニーズに応じて、さまざまなレベルの厳密さでスキルをテストできます。
• Claude.ai での手動テスト - クエリを直接実行し、動作を観察します。速い
繰り返し、セットアップは必要ありません。
• Claude Code でのスクリプト化されたテスト - テスト ケースを自動化して再現可能にします。
