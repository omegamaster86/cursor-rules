# synthesis.md テンプレート（収集ターン必須）

親は runner 収集後、**必ず** `.cursor/multi-agent-candidates/<task-slug>/synthesis.md` を本テンプレに沿って **詳細に** 書く。

**目的:** このファイル **だけ** を読めば、3（または N）エージェントの調査結果・合意・相違・最終判断が分かること。チャット要約のコピペや Runners 表だけでは不十分。

**禁止:**

- 数行のメモだけの `synthesis.md`
- 「各 runner のファイルを見てください」だけで終える
- チャット統合出力と重複だけで、runner 個別の主張を要約しない

---

## 必須セクション（見出し番号は固定推奨）

### 1. 結論（先に読む）

質問への答えを **表形式** で要約（1 ページ以内）。読者がここだけ読んで方向性を掴めること。

| 質問 | 回答 |
|------|------|
| （調査の主質問） | … |
| （サブ質問があれば） | … |

末尾に **一言**（2 文以内）で全体を締める。

### 2. 何を調査したか

- **背景** — なぜこの調査が必要だったか
- **調査質問** — 1 文で引用形式
- **制約** — brief の Constraints を要約（箇条書き）

対象コード・API・swagger があれば **具体例**（JSON 抜粋やパス）を載せる。

### 3. 現行 / 論点の構造（該当する場合）

調査対象の構造を **図・表・コード** で説明。「なぜ複雑に見えるか」を言語化する。

- ツリー図（ASCII）または表
- 各要素の役割と「削ると何が壊れるか」列

### 4. N エージェントの結論サマリ

**比較表必須。** 列: 各 runner（model slug または shape 名）。行: 結論・主要推奨・BE/FE 変更の要否 などタスクに応じた軸。

各行の下に **詳細ファイルへの相対リンク**:

```markdown
- [claude-sonnet-5-thinking-medium.md](./claude-sonnet-5-thinking-medium.md)
```

### 5. 各エージェントの主張（詳細）

**runner ごとにサブ見出し**（`5.1 Sonnet` など）。各ブロックに最低限:

1. **結論**（1〜3 文）
2. **根拠** — コードパス・API・仕様引用（ファイル:行 または swagger 節）
3. **推奨形** — 型スケッチまたは JSON（短くても具体）
4. **検討した代替案** — 表形式（案 | 評価/却下理由）
5. **ベンダー依頼の要否** — 要 / 不要 と理由

runner の全文を丸写ししない。**統合読者向けに要約するが、根拠と代替案は省略しない。**

### 6. 一致点と相違点

- **全員一致** — 箇条書き（強い合意シグナル）
- **相違点** — 表形式（論点 | Runner A | Runner B | …）

### 7. 統合推奨（採用判断）

- **採用したベース** — どの runner（または shape）をベースにしたかと **理由**
- **グラフト** — 敗者から取り込んだ案（元 runner 明記）。任意改善として別チケット化した案もここ
- **却下** — 統合で採用しなかった案と理由

### 8. 簡略化 / 変更できないもの・できるもの（該当する場合）

❌ と ✅ の **2 列表**。対象 | 理由 | 担当（FE / ベンダー）| 状態（未着手 / 実施済み）

タスクが API 簡略化でない場合は「変更範囲の整理」などに読み替える。

### 9. 推奨成果物（採用版）

**コードブロックで全文**（JSON / TypeScript / swagger 抜粋）。要約だけにしない。

### 10. 任意改善案（未採用・該当する場合）

ベースに採用しなかった runner 案を **別形として全文提示**。「なぜ未採用か」を 1 行添える。

### 11. 次のアクション

| 優先 | アクション | 担当 | 状態 |
|------|-----------|------|------|

### 12. Runners 記録

| Model slug / 立場 | Output file | Status | 主な差分 |
|-------------------|-------------|--------|----------|

**Dropout:** `none` または model slug・理由

### 13. ベンダー依頼文骨子（必要時）

依頼が不要なら「本件は FE-only / 変更不要」と明記。必要なら **コピペ可能な依頼文**（背景・要件・維持条件・検証条件）。

### 参照

調査で読んだファイルパス・swagger 節・ルール名。

## 品質チェック（親が自己確認）

収集ターン終了前に満たすこと:

- [ ] `synthesis.md` を **このファイルだけ** 読んで調査結論が分かる
- [ ] 3 runner それぞれに **§5 相当の詳細ブロック** がある
- [ ] 一致点・相違点の **表** がある
- [ ] 採用版の成果物が **コードブロック全文** で載っている
- [ ] チャット本文は要約だが、`synthesis.md` は詳細（チャット ≪ synthesis の情報量）

## チャットとの関係

- **チャット統合出力**（SKILL.md 記載の 5 項目）は収集ターンで必須のまま
- チャットは要約・意思決定の入口。**詳細の正本は `synthesis.md`**
- ユーザーが「統合ファイルだけ見たい」と言ったとき、`synthesis.md` で足りる品質にする
