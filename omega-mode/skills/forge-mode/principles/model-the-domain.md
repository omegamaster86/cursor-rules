# ドメインをモデル化する

状態のあるロジックを書くとき、または分岐・形状仮定がファイルをまたいで増えるときに適用する。ドメインを条件分岐の散在ではなく、構造にエンコードする。

**なぜ:** 散らばった boolean、繰り返される shape 仮定、ファイル横断の branching は偶発的複雑さである。ドメインに合う構造は不正状態を表現不能にし、分岐を消す。書く時点で選ぶのは安い。後から取り出すとリファクタに見え、先送りされる。

`foundational-thinking` が「契約（データ形状）を先に名指しする」なら、本原則は **その形状をドメインに合わせる**。型の構文（判別共用体、brand、網羅 match）は **type-system-discipline** と `web-coding-standards` の `rules/ts-*.md`。

**こういう構造を検討する:**

- 散らばった boolean・フェーズ・ライフサイクルチェックの代わりに **状態機械**
- ゆるい引数や繰り返される shape の代わりに **型付きオブジェクト / モデル**
- ファイル横断の branching の代わりに **map、registry、lookup、判別共用体**
- 場当たりの mutation の代わりに **reducer または command/event**
- load → validate → transform → save のような工程分割ではなく、**1つのドメイン知識を所有するモジュール**（実行順は所有ではない）
- 繰り返される振る舞い・不変条件を集める **小さなモジュール境界**
- アクセスパターンが求めるなら queue、cache、index、graph/tree、正規化したコレクション
- どれも合わなければ、コードが **決して許してはいけないこと** と読み方を決めてから、それをちょうどエンコードする構造を探す

抽象を強制しない。今の形が既に明確・局所的・増えそうにないなら退屈なコードを選ぶ。分岐・重複ルール・不正状態・ライフサイクルリスクを消さない間接参照は疑う。

**skipped の兆候:** 新機能が既存 if/else の末尾に 1 分岐を足す。同期必須の boolean が 2 個目に増える。フェーズ名モジュールが同じドメインルールを工程ごとに繰り返す。

**テスト:**

- 「この boolean はもう一方と同時に true になりうるか？」なりうるなら和型に分割する。
- 「同じ判定が server action / hook / UI に複製されているか？」1つのモデル（または lookup）に集める。
- 「来月ステータスを 1 つ足すとき、コンパイラは直し場所を教えるか？」教えなければモデルが弱い。
