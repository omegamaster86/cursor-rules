# アーキテクチャ批判ルーブリック

関連するレンズを通してレビュー。すべてのサブシステムにすべてが当てはまるわけではない。

## Abstraction Fit

抽象は負荷に見合っているか。

- 各抽象は実概念を表すか、それとも「必要になるかも」ための間接層か。
- 境界は正しい場所か。独立に変わるものを分離しているか。
- コンポーネントが知る必要のない実装詳細を共有する偶発的結合はないか。
- ビジネスロジックはフレームワーク配線と絡み、きれいに分離されているか。

過剰抽象は不足抽象と同様に問題。ドメインが単純なら平坦で単純な設計でよい。

## Data Model

データ構造は実際の使用パターンに合っているか。

- データモデルは実際のアクセスのためか、概念的モデルのためか設計されたか。
- コードが常にデータを再形成するインピーダンスミスマッチはないか。
- 型は正直か。実行時データを表すか、存在以上の構造を主張するか。

## Boundary Discipline

システム境界はきれいで適切に置かれているか。

- 検証はエントリポイントに集中か、内部コードに散在か。
- エラーは境界で処理されきれいに伝播か、各層で catch 再 throw か。
- データはよく型付けされた形で境界を越えるか、optional だらけの袋か。
- このサブシステムは隔離テスト可能か、システム全体の起動が要るか。

## Evolution Readiness

このアーキテクチャはありそうな変更にどれだけ耐えるか。

- 最もありそうな次要件が明日来たら、どれだけ変わるか。「1 ファイル」か「すべて」か。
- 緩和が要るハードコード仮定はないか。
- 設計は後付け（アフタースート）か、最初から計画にあったか（統合）。
- 誰も依存しない互換のためのレガシー経路はないか。

仮説的変更への未対応を罰しない。コードベースの軌道からありそうな変更に焦点。

## Complexity vs. Value

複雑さ予算は賢く使われているか。

- 複雑さは要る部分（コアロジック、難しい不変条件）に集中か、偶発的場所（ボイラープレート、不要間接、設定）か。
- 同じ振る舞いのより単純な方法はないか。
- 各コンポーネントは存在を正当化するか、以前の設計の名残か。

## Consistency

このサブシステムはコードベース他で確立されたパターンに従うか。

- 似た問題は他と同じ解き方か、この領域だけ独自パターンか。
- パターンが違うなら良い理由か、独立進化しただけか。
- 不一致は自動的に悪ではない。説明のない不一致は保守負担。
