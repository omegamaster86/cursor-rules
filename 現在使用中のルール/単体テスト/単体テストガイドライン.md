## 1. 基本概念と目的

### 1.1 単体テストとは

単体テスト（Unit Test）とは、ソフトウェアの最小単位である「単体」（関数、メソッド、クラスなど）を個別にテストする手法です。

**例：**
```javascript
// テスト対象の関数
function calculateDiscount(price, discountRate) {
    if (price < 0 || discountRate < 0) {
        throw new Error("価格と割引率は0以上である必要があります");
    }
    return price * (1 - discountRate);
}

// 単体テスト
describe('calculateDiscount', () => {
    test('正常ケース: 10%割引', () => {
        expect(calculateDiscount(1000, 0.1)).toBe(900);
    });
    
    test('異常ケース: 負の価格', () => {
        expect(() => calculateDiscount(-100, 0.1))
            .toThrow("価格と割引率は0以上である必要があります");
    });
});
```

このように、各単体が仕様通りに動作することを検証し、バグを早期に発見・修正することを目的とします。

### 1.2 単体テストの特徴

#### 1.2.1 独立性
他のコンポーネントに依存せず、単体で実行可能な特性です。

**重要性:**
- テストの実行順序に依存しない
- 他のテストの結果に影響されない
- 並列実行が可能

**実装例:**
```javascript
// ❌ 依存関係がある例
function getUserName(userId) {
    const user = database.getUser(userId); // データベースに依存
    return user.name;
}

// ✅ 独立性を保った例
function getUserName(user) {
    return user.name;
}

// テストではモックを使用
test('getUserName', () => {
    const mockUser = { name: '田中太郎' };
    expect(getUserName(mockUser)).toBe('田中太郎');
});
```

#### 1.2.2 高速性
実行時間が短く、頻繁に実行できる特性です。

**目標:**
- 1つのテスト: 数ミリ秒〜数秒以内
- 全体のテストスイート: 10分以内
- 開発中のフィードバック: 即座に結果が分かる

**高速化のポイント:**
```javascript
// ❌ 遅い例（実際のAPI呼び出し）
test('fetchUserData', async () => {
    const data = await fetch('/api/users/123'); // ネットワーク遅延
    expect(data.name).toBe('田中太郎');
});

// ✅ 高速な例（モック使用）
test('fetchUserData', () => {
    const mockData = { name: '田中太郎' };
    const result = processUserData(mockData);
    expect(result.name).toBe('田中太郎');
});
```

#### 1.2.3 自動化
手動操作なしで自動実行可能な特性です。

**自動化のメリット:**
- CI/CDパイプラインでの自動実行
- コード変更時の即座な検証
- 人的ミスの排除

**自動化の実装:**
```javascript
// package.json
{
  "scripts": {
    "test": "jest",
    "test:watch": "jest --watch",
    "test:coverage": "jest --coverage"
  }
}

// GitHub Actions例
// .github/workflows/test.yml
name: Tests
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v2
      - name: Run tests
        run: npm test
```

#### 1.2.4 再現性
同じ条件で何度でも同じ結果が得られる特性です。

**再現性の重要性:**
- バグの特定が容易
- テスト結果の信頼性
- 環境に依存しない

**再現性を保つ方法:**
```javascript
// ❌ 再現性がない例
test('randomNumber', () => {
    const random = Math.random(); // 毎回異なる値
    expect(random).toBeGreaterThan(0);
});

// ✅ 再現性がある例
test('calculateTax', () => {
    const price = 1000;
    const taxRate = 0.1;
    const result = calculateTax(price, taxRate);
    expect(result).toBe(100); // 常に同じ結果
});

// 日付の固定
test('formatDate', () => {
    const fixedDate = new Date('2024-01-01');
    const result = formatDate(fixedDate);
    expect(result).toBe('2024/01/01');
});
```

### 1.3 単体テストの目的

#### 1.3.1 品質保証
- **バグの早期発見**: 開発段階で問題を特定し、修正コストを削減
- **仕様の検証**: 実装が要求仕様を満たしていることを確認
- **回帰テスト**: 既存機能が新機能追加時に壊れていないことを確認

**回帰テストとは:**
「回帰」とは「元に戻る」という意味で、新しく追加した機能や修正が、既存の機能に悪影響を与えていないかを確認するテストです。

**なぜ回帰テストが必要？**
```javascript
// 例：ユーザー管理システム
// 既存機能：ユーザー登録
function registerUser(userData) {
    // バリデーション
    if (!userData.email || !userData.password) {
        throw new Error('必須項目が不足しています');
    }
    
    // パスワードハッシュ化
    const hashedPassword = hashPassword(userData.password);
    
    // データベース保存
    return saveUser({
        ...userData,
        password: hashedPassword
    });
}

// 新機能追加：パスワード強度チェック
function validatePasswordStrength(password) {
    if (password.length < 8) {
        throw new Error('パスワードは8文字以上である必要があります');
    }
    return true;
}

// ❌ 問題のある実装：既存機能を壊してしまう
function registerUser(userData) {
    // 新機能を追加したが、既存のバリデーションを削除
    validatePasswordStrength(userData.password); // 新しいチェック
    
    const hashedPassword = hashPassword(userData.password);
    return saveUser({
        ...userData,
        password: hashedPassword
    });
    // 既存のemailチェックが削除されてしまった！
}

// ✅ 正しい実装：既存機能を保持
function registerUser(userData) {
    // 既存のバリデーションを保持
    if (!userData.email || !userData.password) {
        throw new Error('必須項目が不足しています');
    }
    
    // 新機能を追加
    validatePasswordStrength(userData.password);
    
    const hashedPassword = hashPassword(userData.password);
    return saveUser({
        ...userData,
        password: hashedPassword
    });
}
```

**回帰テストの例:**
```javascript
describe('ユーザー登録機能の回帰テスト', () => {
    test('既存機能：emailとpasswordが必須', () => {
        // 既存のテストケースが引き続き動作することを確認
        expect(() => registerUser({})).toThrow('必須項目が不足しています');
        expect(() => registerUser({ email: 'test@example.com' })).toThrow('必須項目が不足しています');
    });
    
    test('新機能：パスワード強度チェック', () => {
        // 新機能が正しく動作することを確認
        expect(() => registerUser({
            email: 'test@example.com',
            password: '123' // 8文字未満
        })).toThrow('パスワードは8文字以上である必要があります');
    });
    
    test('統合：既存機能と新機能の両方が動作', () => {
        // 両方の機能が同時に動作することを確認
        const result = registerUser({
            email: 'test@example.com',
            password: 'password123' // 8文字以上
        });
        expect(result).toBeDefined();
    });
});
```

**回帰テストの重要性:**
- **予期しないバグの防止**: 新機能追加時に既存機能が壊れることを防ぐ
- **品質の維持**: システム全体の品質を保つ
- **開発の安心感**: 既存機能を壊す心配なく新機能を追加できる
- **コスト削減**: 本番環境でのバグ発見を防ぎ、修正コストを削減

#### 1.3.2 開発効率の向上
- **リファクタリングの安全性**: コード改善時の動作保証
- **設計の改善**: テストしやすいコード設計の促進
- **ドキュメント機能**: コードの使用方法を示す生きたドキュメント

#### 1.3.3 チーム開発の支援
- **知識共有**: コードの意図と動作を明確化
- **品質基準の統一**: チーム全体での品質レベル維持
- **継続的インテグレーション**: CI/CDパイプラインでの自動品質チェック

### 1.4 単体テストの対象範囲

#### 1.4.1 テスト対象
- **ビジネスロジック**: コアとなる処理ロジック
- **ユーティリティ関数**: 共通で使用される関数
- **データ変換処理**: 入力データの検証・変換処理
- **計算処理**: 数値計算やアルゴリズム

#### 1.4.2 テスト対象外
- **外部システム連携**: 外部API、ファイルシステム
- **UIコンポーネント**: ユーザーインターフェース
- **設定ファイル**: 環境設定や設定値
- **インフラストラクチャ**: サーバー、ネットワーク設定

**注意**: データベース自体は外部システムですが、SQLクエリのロジックやデータベース操作のビジネスロジックは単体テストの対象です。実際のデータベース接続ではなく、モックやインメモリデータベースを使用してテストします。

### 1.5 単体テストの価値

#### 1.5.1 短期的価値
- **デバッグ時間の短縮**: 問題の特定と修正が迅速
- **品質の向上**: バグの混入率を大幅に削減
- **開発速度の向上**: 安心してコードを変更できる

#### 1.5.2 長期的価値
- **保守性の向上**: コードの理解と修正が容易
- **技術的負債の削減**: 品質の高いコードベースの維持
- **チームの生産性向上**: 品質に対する不安の解消

### 1.6 成功の指標

#### 1.6.1 量的指標
- **コードカバレッジ**: 80%以上を目標
- **テスト実行時間**: 全体で10分以内
- **テスト数**: 機能数に対する適切な比率

#### 1.6.2 質的指標
- **バグ発見率**: 本番環境でのバグ発生率の低下
- **修正時間**: バグ修正にかかる時間の短縮
- **開発速度**: 機能追加・変更の速度向上

## 2. テストの種類と分類

### 2.1 テストの分類方法

テストは様々な観点から分類できます。単体テストを理解するために、まずテスト全体の分類を把握しましょう。

#### 2.1.1 テストレベルによる分類

**1. 単体テスト（Unit Test）**
- **対象**: 個別の関数、メソッド、クラス
- **目的**: 最小単位の動作検証
- **実行頻度**: 開発中に頻繁に実行

**2. 統合テスト（Integration Test）**
- **対象**: 複数のコンポーネント間の連携
- **目的**: インターフェースの動作検証
- **実行頻度**: 機能完成後に実行

**3. システムテスト（System Test）**
- **対象**: システム全体
- **目的**: 要件仕様の検証
- **実行頻度**: リリース前に実行

**4. 受け入れテスト（Acceptance Test）**
- **対象**: ユーザー視点での機能
- **目的**: ビジネス要件の検証
- **実行頻度**: 最終確認時に実行

#### 2.1.2 テスト手法による分類

**1. ホワイトボックステスト**
- **特徴**: 内部構造に基づくテスト
- **対象**: コードの実装詳細
- **例**: 分岐条件、ループ処理

```javascript
// ホワイトボックステストの例
function calculateGrade(score) {
    if (score >= 90) return 'A';      // 分岐1
    if (score >= 80) return 'B';      // 分岐2
    if (score >= 70) return 'C';      // 分岐3
    return 'F';                       // 分岐4
}

describe('calculateGrade ホワイトボックステスト', () => {
    test('分岐1: 90点以上でA', () => {
        expect(calculateGrade(95)).toBe('A');
    });
    
    test('分岐2: 80-89点でB', () => {
        expect(calculateGrade(85)).toBe('B');
    });
    
    test('分岐3: 70-79点でC', () => {
        expect(calculateGrade(75)).toBe('C');
    });
    
    test('分岐4: 70点未満でF', () => {
        expect(calculateGrade(65)).toBe('F');
    });
});
```

**2. ブラックボックステスト**
- **特徴**: 入力と出力に基づくテスト
- **対象**: 仕様に基づく動作
- **例**: 境界値、等価分割

```javascript
// ブラックボックステストの例
function validateAge(age) {
    return age >= 0 && age <= 150;
}

describe('validateAge ブラックボックステスト', () => {
    test('有効な年齢範囲', () => {
        expect(validateAge(25)).toBe(true);
        expect(validateAge(0)).toBe(true);
        expect(validateAge(150)).toBe(true);
    });
    
    test('無効な年齢範囲', () => {
        expect(validateAge(-1)).toBe(false);
        expect(validateAge(151)).toBe(false);
    });
});
```

### 2.2 単体テストの詳細分類

#### 2.2.1 テストケースの種類

**1. 正常系テスト（Happy Path）**
- **目的**: 期待通りの動作を確認
- **例**: 正常な入力値での処理結果

```javascript
test('正常系: 有効なユーザー情報で登録', () => {
    const userData = {
        name: '田中太郎',
        email: 'tanaka@example.com',
        age: 25
    };
    
    const result = registerUser(userData);
    expect(result.success).toBe(true);
    expect(result.userId).toBeDefined();
});
```

**2. 異常系テスト（Error Handling）**
- **目的**: エラー処理の動作を確認
- **例**: 無効な入力値でのエラーハンドリング

```javascript
test('異常系: 無効なメールアドレス', () => {
    const userData = {
        name: '田中太郎',
        email: 'invalid-email',
        age: 25
    };
    
    expect(() => registerUser(userData))
        .toThrow('有効なメールアドレスを入力してください');
});
```

**3. 境界値テスト（Boundary Value）**
- **目的**: 境界値での動作を確認
- **例**: 最小値、最大値、境界付近の値

```javascript
test('境界値: 年齢の境界値テスト', () => {
    // 最小値
    expect(validateAge(0)).toBe(true);
    expect(validateAge(-1)).toBe(false);
    
    // 最大値
    expect(validateAge(150)).toBe(true);
    expect(validateAge(151)).toBe(false);
    
    // 境界付近
    expect(validateAge(1)).toBe(true);
    expect(validateAge(149)).toBe(true);
});
```

#### 2.2.2 テストデータの分類

**1. 正常データ**
- **特徴**: 期待通りの動作をするデータ
- **例**: 有効な形式の入力値

**2. 異常データ**
- **特徴**: エラーを引き起こすデータ
- **例**: 無効な形式、null、undefined

**3. 境界データ**
- **特徴**: 境界値やその近傍のデータ
- **例**: 最小値、最大値、空文字列

```javascript
// テストデータの例
const testData = {
    normal: {
        validUser: { name: '田中太郎', email: 'tanaka@example.com' },
        validProduct: { name: '商品A', price: 1000 }
    },
    abnormal: {
        invalidEmail: { name: '田中太郎', email: 'invalid' },
        negativePrice: { name: '商品B', price: -100 }
    },
    boundary: {
        emptyName: { name: '', email: 'test@example.com' },
        maxLengthName: { name: 'A'.repeat(100), email: 'test@example.com' }
    }
};
```

### 2.3 テストの実行タイミング

#### 2.3.1 開発フェーズ別のテスト

**1. 開発中テスト**
- **タイミング**: コード記述中
- **目的**: 即座なフィードバック
- **ツール**: IDE統合、ウォッチモード

**2. コミット前テスト**
- **タイミング**: Gitコミット前
- **目的**: 品質の確保
- **ツール**: pre-commitフック

**3. CI/CDテスト**
- **タイミング**: プッシュ後
- **目的**: 継続的品質管理
- **ツール**: GitHub Actions、Jenkins

```javascript
// package.jsonでのテスト設定例
{
  "scripts": {
    "test": "jest",
    "test:watch": "jest --watch",
    "test:coverage": "jest --coverage",
    "test:ci": "jest --ci --coverage --watchAll=false"
  },
  "husky": {
    "hooks": {
      "pre-commit": "npm run test:ci"
    }
  }
}
```

### 2.4 テストの優先度

#### 2.4.1 テストの重要度

**1. 必須テスト（Critical）**
- **対象**: コア機能、ビジネスロジック
- **優先度**: 最高
- **例**: 決済処理、認証機能

**2. 重要テスト（Important）**
- **対象**: 主要機能
- **優先度**: 高
- **例**: データ処理、計算ロジック

**3. 推奨テスト（Recommended）**
- **対象**: 補助機能
- **優先度**: 中
- **例**: ユーティリティ関数

**4. オプションテスト（Optional）**
- **対象**: 非重要機能
- **優先度**: 低
- **例**: 表示フォーマット、ログ出力

```javascript
// テストの優先度をコメントで明示
describe('決済処理', () => {
    // Critical: ビジネスロジックの核心
    test('正常な決済処理', () => {
        // 必須のテストケース
    });
    
    // Important: エラーハンドリング
    test('残高不足時の処理', () => {
        // 重要なテストケース
    });
    
    // Recommended: 補助機能
    test('決済履歴の記録', () => {
        // 推奨のテストケース
    });
});
```

## 3. テスト設計の原則とベストプラクティス

### 3.1 FIRST原則

FIRST原則は、優れた単体テストの特徴を表す重要な原則です。

#### 3.1.1 Fast（高速）

テストは高速に実行される必要があります。

**重要性:**
- 開発中の即座なフィードバック
- CI/CDパイプラインでの効率的な実行
- 開発者の生産性向上

**実装例:**
```javascript
// ❌ 遅い例：実際のAPI呼び出し
test('ユーザー情報取得', async () => {
    const user = await fetchUserFromAPI(123); // ネットワーク遅延
    expect(user.name).toBe('田中太郎');
});

// ✅ 高速な例：モック使用
test('ユーザー情報取得', () => {
    const mockUser = { id: 123, name: '田中太郎' };
    const result = processUserData(mockUser);
    expect(result.name).toBe('田中太郎');
});
```

#### 3.1.2 Independent（独立）

各テストは他のテストに依存せず、独立して実行できる必要があります。

**重要性:**
- テストの実行順序に依存しない
- 並列実行が可能
- デバッグが容易

**実装例:**
```javascript
// ❌ 依存関係がある例
let globalCounter = 0;

test('カウンター増加1', () => {
    globalCounter++;
    expect(globalCounter).toBe(1);
});

test('カウンター増加2', () => {
    globalCounter++; // 前のテストに依存
    expect(globalCounter).toBe(2);
});

// ✅ 独立した例
test('カウンター増加1', () => {
    const counter = new Counter();
    counter.increment();
    expect(counter.getValue()).toBe(1);
});

test('カウンター増加2', () => {
    const counter = new Counter();
    counter.increment();
    expect(counter.getValue()).toBe(1); // 独立して実行
});
```

#### 3.1.3 Repeatable（再現可能）

同じ条件で何度でも同じ結果が得られる必要があります。

**重要性:**
- テスト結果の信頼性
- 環境に依存しない
- バグの特定が容易

**実装例:**
```javascript
// ❌ 再現性がない例
test('ランダム数値生成', () => {
    const random = Math.random();
    expect(random).toBeGreaterThan(0);
});

// ✅ 再現性がある例
test('固定数値での計算', () => {
    const result = calculateTax(1000, 0.1);
    expect(result).toBe(100); // 常に同じ結果
});

// 日付の固定
test('日付フォーマット', () => {
    const fixedDate = new Date('2024-01-01');
    const result = formatDate(fixedDate);
    expect(result).toBe('2024/01/01');
});
```

#### 3.1.4 Self-Validating（自己検証）

テストは実行結果が明確で、手動での確認が不要である必要があります。

**重要性:**
- 自動化された判定
- 明確な成功/失敗の判定
- 人的ミスの排除

**実装例:**
```javascript
// ❌ 手動確認が必要な例
test('計算結果の確認', () => {
    const result = complexCalculation(100, 200);
    console.log('結果:', result); // 手動で確認が必要
    // アサーションがない
});

// ✅ 自己検証の例
test('計算結果の確認', () => {
    const result = complexCalculation(100, 200);
    expect(result).toBe(300); // 自動で判定
});
```

#### 3.1.5 Timely（適時）

テストは適切なタイミングで書かれる必要があります。

**重要性:**
- テストファースト開発（TDD）
- リファクタリングの安全性
- バグの早期発見

**実装例:**
```javascript
// TDDの例：テストファースト
// 1. まずテストを書く
test('割引計算', () => {
    expect(calculateDiscount(1000, 0.1)).toBe(900);
});

// 2. 最小限の実装
function calculateDiscount(price, rate) {
    return price * (1 - rate);
}

// 3. リファクタリング
function calculateDiscount(price, rate) {
    if (price < 0 || rate < 0) {
        throw new Error('負の値は無効です');
    }
    return price * (1 - rate);
}
```

## 4. テストケース作成指針

### 4.1 テストケース作成の基本プロセス

#### 4.1.1 要件分析

テストケースを作成する前に、テスト対象の要件を明確に理解する必要があります。

**要件分析の手順:**
1. **機能仕様の確認**: 何をする機能か
2. **入力条件の整理**: どのような入力を受け付けるか
3. **出力条件の整理**: どのような出力を返すか
4. **エラー条件の整理**: どのような場合にエラーになるか

```txt
// 例：ユーザー登録機能の要件分析
/*
要件:
- ユーザー名（必須、1-50文字）
- メールアドレス（必須、有効な形式）
- 年齢（必須、0-150歳）
- パスワード（必須、8文字以上）

正常系:
- 有効な情報で登録成功
- ユーザーIDが返される

異常系:
- 必須項目の不足
- 無効な形式の入力
- 年齢範囲外
- パスワードが短すぎる
*/
```

#### 4.1.2 テストケース設計

要件分析に基づいて、包括的なテストケースを設計します。

**設計のポイント:**
- **正常系**: 期待通りの動作
- **異常系**: エラーハンドリング
- **境界値**: 最小値、最大値、境界付近
- **エッジケース**: 特殊な条件

```javascript
// テストケース設計例
const testCases = {
```

```javascript
export function add(a, b) {

    if (typeof a !== 'number' || typeof b !== 'number') {
        throw new Error('引数は数値である必要があります');
    }
    if (b === 0) {
        throw new Error('ゼロで割ることはできません');
    }
    return a / b;
}
```
