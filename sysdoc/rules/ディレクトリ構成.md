# ディレクトリ構成 - Web（Next.js）
## 1. 基本方針

Next.js App Router を使用した Web アプリケーションのディレクトリ構成について説明します。

### コンポーネント配置の基本原則

**コロケーション原則**を採用し、コンポーネントやロジックを適切な場所に配置します：

- `app/[ページ]/_actions/` - そのページで使用するServer Actions（フォーム処理など）
- `app/[ページ]/_apis/` - そのページで使用するAPIクライアント
- `app/[ページ]/_components/` - そのページでのみ使用するコンポーネント
- `components/` - 複数ページで共有するコンポーネント

## 4. 各ディレクトリの役割

### 4.1 `app/` - App Router

**概念的な構成**:

```
Next.js App Router
├── Server Components（サーバーサイドレンダリング）
│   ├── データフェッチ（UI表示用。BFF/Edge Functions経由・ビジネスロジックは持たない）
│   ├── 初期HTML生成
│   └── SEO最適化
├── Client Components（クライアントサイド）
│   ├── インタラクティブUI
│   ├── 状態管理
│   └── ユーザー入力
├── BFF（Route Handlers）
│   ├── 入力検証・セッション連携・レート制限・キャッシュ制御
│   └── Edge Functions の呼び出し（supabase.functions.invoke）
└── Server Actions（サーバー関数）
    ├── UI補助のサーバ処理（ビジネスロジックはEdge Functionsへ）
    └── 軽微なデータ変更のトリガー
```

**役割**:
- ページとレイアウトの定義
- ルーティング構造の管理
- ページグループ化（`(group)`）によるレイアウト共有
- BFF は薄いゲートウェイとして機能し、ビジネスロジック/DB操作は Edge Functions に一元化
- 外部Webhookや長時間処理などは Edge Functions 側で実装

### 4.2 `components/` - 共通コンポーネント

**役割**:
- 複数ページで使用される共通コンポーネント
- UI コンポーネントライブラリ
- レイアウトコンポーネント

**配置ルール**:
- `apis/` - 共通APIクライアント（複数ページで使用）
- `components/ui/` - 基本的な UI コンポーネント（Button, Input, Modal など）
- `components/layouts/` - レイアウトコンポーネント（Header, Footer など）
- 各コンポーネントは独立したディレクトリに配置
- テストファイルは `__tests__/` ディレクトリに集約し、Storybook ファイル（`.stories.tsx`）はコンポーネント直下に配置する

### 4.3 `hooks/` - カスタムフック

**役割**:
- アプリケーション全体で使用するカスタムフック
- React Hooks の共通ロジック

### 4.4 `services/` - 外部サービス設定

**役割**:
- 外部サービスの設定とクライアント

**構成**:
- `services/supabase-service/` - Supabase クライアントの設定

### 4.5 `utils/` - ヘルパー関数

**役割**:
- アプリケーション全体で使用するヘルパー関数
- 共通のユーティリティ関数

### 4.6 `types/` - 型定義

**役割**:
- TypeScript の型定義
- データベース型定義（自動生成）
- グローバルな型定義

### 4.7 `supabase/` - Supabase 関連（srcと並列）

**役割**:
- Supabase プロジェクトの設定
- データベースマイグレーション
- Database Functions（PostgreSQL関数）
- Edge Functions

**配置**: `src/`ディレクトリと同じ階層に配置（プロジェクトルート直下）

**詳細**:

#### `supabase/config.toml`
- Supabase プロジェクトの設定ファイル
- プロジェクト ID、API エンドポイント、認証設定、メール設定などを定義
- ローカル開発環境の設定を管理

#### `supabase/migrations/`
- データベースマイグレーションファイル
- ファイル名形式: `YYYYMMDDHHMMSS_migration_name.sql`
- テーブル定義、Database Functions、インデックス、RLS ポリシーなどの SQL 文を記述
- マイグレーションは時系列順に実行される
- `supabase migration new [name]` コマンドで新規作成

#### `supabase/db-functions/`（オプション）
- Database Functions（PostgreSQL関数）の開発用ワーキングディレクトリ
- 完成した関数は `migrations/` に移して本番適用
- 機能別にサブディレクトリを作成（例: `users/`, `orders/`）
- 小規模プロジェクトでは不要（migrations のみで管理）

> 📖 **詳細**: Database Functions の管理方法は [`03_Supabase実装ガイド_Web.md`](03_Supabase実装ガイド_Web.md) の「3.2 Database Functions の管理方法」を参照

#### `supabase/functions/[function-name]/`
- 各 Edge Function ごとにディレクトリを作成
- `index.ts`: Edge Function のエントリーポイント（必須）
- 各 Edge Function は独立して実行可能な単位とする
- 共通コードが必要な場合は以下のいずれかの方法を使用：
  - 各 Function 内で必要な関数を定義（小規模な場合）
  - npm パッケージとして管理し、import して使用（大規模な場合）
- 外部パッケージの使用は Deno の標準ライブラリまたは ESM 対応パッケージに限定

## 5. コンポーネント・ロジック配置ルール

### 5.1 ページ固有のServer Actions

**配置場所**: `app/[ページ]/_actions/`

**ルール**:
- そのページで使用するServer Actions（フォーム処理、データ更新など）
- コロケーション原則に従い、使用する場所の近くに配置
- `_actions` ディレクトリはルーティングに影響しない
- ファイル名: リソース名（例: `todo.ts`, `user.ts`）

**例**:
```
app/
├── todos/
│   ├── new/
│   │   ├── _actions/
│   │   │   └── todo.ts        # createTodo Server Action
│   │   ├── _components/
│   │   │   └── NewTodoForm/
│   │   └── page.tsx
│   └── [id]/
│       ├── edit/
│       │   ├── _actions/
│       │   │   └── todo.ts    # updateTodo Server Action
│       │   └── page.tsx
```

**コード例**:
```typescript
// app/todos/new/_actions/todo.ts
"use server";

export type CreateTodoState = {
  success: boolean;
  message: string;
};

export async function createTodo(
  prevState: CreateTodoState,
  formData: FormData,
): Promise<CreateTodoState> {
  // Server Action実装
}
```

### 5.2 ページ固有のコンポーネント

**配置場所**: `app/[ページ]/_components/`

**ルール**:
- そのページでのみ使用するコンポーネント
- コロケーション原則に従い、使用する場所の近くに配置
- `_components` ディレクトリはルーティングに影響しない

**例**:
```
app/
├── login/
│   ├── _actions/
│   │   └── auth.ts
│   ├── _components/
│   │   ├── LoginForm/
│   │   │   └── index.tsx
│   │   └── SocialLoginButtons/
│   │       └── index.tsx
│   └── page.tsx
```

### 5.3 共通コンポーネント

**配置場所**: `components/`

**ルール**:
- 複数ページで使用されるコンポーネント
- 再利用性が高いコンポーネント
- UI ライブラリのようなコンポーネント

**例**:
```
components/
├── ui/
│   ├── Button/
│   │   ├── index.tsx
│   │   ├── Button.stories.tsx
│   │   └── __tests__/
│   │       └── Button.test.tsx
│   └── Input/
│       ├── index.tsx
│       ├── Input.stories.tsx
│       └── __tests__/
│           └── Input.test.tsx
```

## 6. APIクライアント配置ルール

**コロケーション原則**を採用し、APIクライアントを適切な場所に配置します：

- `app/[ページ]/_apis/` - そのページでのみ使用するAPIクライアント
- `apis/` - 複数ページで共有するAPIクライアント

### 6.1 ページ固有のAPIクライアント

**配置場所**: `app/[ページ]/_apis/`

**ルール**:
- そのページでのみ使用するAPIクライアント
- コロケーション原則に従い、使用する場所の近くに配置
- `_apis` ディレクトリはルーティングに影響しない
- リソース単位でファイルを配置
- ドット記法を使用してサーバー用とクライアント用を区別
  - `[resource].server.ts` - サーバー用APIクライアント（全HTTPメソッド）
  - `[resource].client.ts` - クライアント用APIクライアント（GETのみ）

**例**:
```
app/
├── login/
│   ├── _apis/
│   │   ├── auth.server.ts   # サーバー用APIクライアント
│   │   └── auth.client.ts   # クライアント用APIクライアント（GETのみ）
│   ├── _components/
│   └── page.tsx
```

**コード例**:
```typescript
// app/login/_apis/auth.server.ts (サーバーサイド用)
'use server'

export async function loginUser(email: string, password: string) { /* ... */ }
export async function logoutUser() { /* ... */ }

// app/login/_apis/auth.client.ts (クライアントサイド用 - GETのみ)
'use client'

export async function getLoginStatus() { /* ... */ }
```

### 6.2 共通APIクライアント

**配置場所**: `apis/`

**ルール**:
- 複数ページで使用されるAPIクライアント
- 再利用性が高いAPIクライアント
- リソース単位でファイルを配置
- ドット記法を使用してサーバー用とクライアント用を区別

**例**:
```
apis/
├─ users.server.ts      # サーバー用APIクライアント
├─ users.client.ts      # クライアント用APIクライアント（GETのみ）
├─ orders.server.ts
└─ orders.client.ts
```

**コード例**:
```typescript
// apis/users.server.ts (サーバーサイド用)
'use server'

export async function getUsers() { /* ... */ }
export async function createUser(data) { /* ... */ }
export async function updateUser(id, data) { /* ... */ }
export async function deleteUser(id) { /* ... */ }

// apis/users.client.ts (クライアントサイド用 - GETのみ)
'use client'

export async function getUsers() { /* ... */ }
export async function getUserById(id) { /* ... */ }
```

## 7. ファイル命名規則

### 7.1 ページファイル

- `page.tsx` - ページコンポーネント
- `layout.tsx` - レイアウトコンポーネント
- `loading.tsx` - ローディング UI
- `error.tsx` - エラー UI
- `not-found.tsx` - 404 ページ

### 7.2 コンポーネントファイル

- `index.tsx` - コンポーネント本体
- `__tests__/[ComponentName].test.tsx` - テストファイル（テストは `__tests__/` に集約）
- `[ComponentName].stories.tsx` - Storybook ファイル
- `[ComponentName].module.css` - CSS Modules（使用する場合）

### 7.3 ユーティリティファイル

- `camelCase.ts` - 関数名と同じ名前（例: `formatDate.ts`）
- `index.ts` - エクスポート用のインデックスファイル

## 9. ベストプラクティス

### 9.1 コンポーネント設計

- **単一責任の原則**: 1 つのコンポーネントは 1 つの責務のみを持つ
- **コンポーネントの細分化**: 大きなコンポーネントは小さく分割する
- **再利用性**: 共通部分は積極的に共通コンポーネント化する

### 9.2 Server Actions設計

- **コロケーション原則**: ページ固有の`_actions/`ディレクトリに配置
- **ファイル命名**: リソース名で命名（例: `todo.ts`, `user.ts`）
- **状態型のエクスポート**: Server Actionの戻り値の型を定義してエクスポート（例: `CreateTodoState`）
- **Zodバリデーション**: FormDataのバリデーションは必ずサーバー側でZodを使用
- **useActionStateとの統合**: `useActionState`で使用できるように、第一引数に`prevState`、第二引数に`FormData`を受け取る

### 9.3 APIクライアント設計

- **コロケーション優先**: まずページ固有の`_apis/`に配置し、再利用が必要になったら`apis/`に移動
- **サーバー/クライアント分離**: `.server.ts`と`.client.ts`を明確に分ける
- **クライアントはGETのみ**: セキュリティ上、クライアント側ではGETメソッドのみを使用
- **Server Actionsを活用**: データ変更は`'use server'`を使用したServer Actionsで実装
- **呼び出しラッパの選択**: Edge Functions の呼び出しは、再利用/共通化が必要なら`services/functions/`に集約。不要なら BFF の`app/api/*/route.ts`内から直接`supabase.functions.invoke('<fn>')`で十分

### 9.4 Server Components と Client Components

- **デフォルトは Server Components**: 可能な限り Server Components を使用
- **Client Components の最小化**: インタラクティブな部分のみ Client Components にする
- **'use client' の配置**: Client Components の最上部に `'use client'` ディレクティブを記述
- **Server/Client分離**: ページ（Server Component）とフォーム（Client Component）を明確に分離

### 9.5 ディレクトリ構成の拡張

プロジェクトの成長に応じて、以下のディレクトリを追加することを検討：

- `src/features/` - 機能別のコンポーネントとロジックをまとめる（Feature-First アプローチ）
- `src/contexts/` - React Context の定義
- `src/stores/` - 状態管理ライブラリのストア
- `src/constants/` - 定数定義
- `src/config/` - 設定ファイル
